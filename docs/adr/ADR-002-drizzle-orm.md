# ADR-002: Use Drizzle ORM for Supabase data access

- **Status:** Accepted — 2026-08 pivot
- **Deciders:** Pedro Klein (dev)
- **Depends on:** [ADR-001](ADR-001-drop-sheets.md) — Supabase became the source of truth

## Context

ADR-001 promoted Supabase Postgres to source of truth. That surfaced a data-access decision: how do we talk to Postgres in this Next.js 16 codebase? Three candidates were evaluated:

1. **`@supabase/supabase-js` + `supabase gen types typescript`**
2. **Prisma**
3. **Drizzle ORM**

Constraints:
- This is a PoC, not production. Iteration speed matters more than defense in depth.
- Agentic development — most code will be written by agents; typed queries are worth extra than they'd be for a human-only team.
- The primary shape is `patients` (base table) joined to condition-specific extension tables (`gestantes_data`, `tuberculose_data`, `has_data`). Base + extension joins are the dominant query.
- No real patient data will live in the DB during PoC (per LGPD guard, synthetic seed only).
- Supabase Row Level Security (RLS) may become important when productionizing but is not enforced in the PoC.

## Decision

**Drizzle ORM** for all data queries, mutations, and migrations. `@supabase/ssr` remains for authentication (see `auth-betterauth` skill). No `.from(...)` calls via `@supabase/supabase-js` anywhere in the codebase.

**Legacy SQL migrations (`supabase/migrations/001..003.sql`) are deleted.** New Drizzle-generated migrations start from `0001` during pivot execution.

Boundary rules (enforced by the `drizzle-data-access` skill):
- Schema lives in `src/db/schema/*.ts` as Drizzle TypeScript definitions.
- Migrations are SQL files, generated by `drizzle-kit generate`, committed to `supabase/migrations/`.
- One DB client, at `src/db/client.ts`, imported everywhere.
- Service-role DB access is restricted to admin scripts (seed, backups) — never used from user-facing route handlers.
- A pre-DB-mutation gate must be added to any script that runs `drizzle-kit push` or `drizzle-kit migrate` — verifies the target Supabase project is non-production before proceeding.

## Consequences

**Positive:**
- **Best agent DX for typed CRUD.** `db.query.patients.findFirst({ where: eq(patients.cns, cns), with: { gestantes: true } })` is legible and IDE-completed.
- **SQL-native migrations.** `drizzle-kit generate` produces plain `.sql` we commit and inspect — no proprietary migration history table.
- **RLS-friendly** (relative to Prisma). If we later enable RLS, Drizzle can be configured to use the user's JWT via session variables; Prisma bypasses RLS by default with a service-role connection.
- **No code-generation step.** Types are inferred from schema definitions (`typeof patients.$inferSelect`), no build step to run before typechecking works.
- **Portable.** Drizzle isn't tied to Supabase — if we ever move Postgres providers, migrations and queries survive.

**Negative / accepted trade-offs:**
- **No RLS in MVP.** Row-level policies are a production-hardening step deferred to when the pilot expands. Compensating controls: explicit user-check gates in every route handler, service-role usage restricted to admin scripts, LGPD guard enforced on all seeds.
- **Legacy Supabase tables in the running project are orphaned.** Deleting the migration files does not drop tables; the running Supabase project keeps `coordinates_cache`, `sync_metadata`, `manual_pins`, etc. Pivot execution will either wipe and recreate via Drizzle-generated migrations OR write a targeted `DROP TABLE` migration for the dead ones.
- **Less mainstream than Prisma.** Fewer tutorials, smaller ecosystem. Accepted because the DX gap for this codebase is small and the RLS story is meaningfully better.

## Alternatives considered

- **Prisma.** Rejected primarily for the **service-role RLS bypass footgun**: Prisma connects with a superuser connection string by default, so if we ever turn on RLS and forget to configure Prisma's session-variable extension, RLS becomes cosmetic. Also introduces a dual migration system (Prisma's history table vs. `supabase/migrations/`) and a code-generation step. Best pure DX but wrong fit for a project that will eventually enforce RLS.
- **`@supabase/supabase-js` + generated types.** Rejected because base+extension joins via `.select("*, gestantes_data(*)")` are stringly-typed, hard to refactor, and mix concerns (auth SDK doing DB queries). Not needed at all in this codebase — all data access is Drizzle-only, and Better Auth handles sessions via its own SQLite store.

## Rollback plan

If the Drizzle choice proves wrong post-pivot:
- **Legacy SQL migrations are preserved in git history**, marked by the tag `pre-pivot-migrations`. Recover with:
  ```bash
  # One-liner (preferred):
  git checkout pre-pivot-migrations -- supabase/migrations/

  # Or find the deletion commit and check out its parent:
  git log --diff-filter=D --summary -- supabase/migrations/
  git checkout <hash>~1 -- supabase/migrations/
  ```
- **Drizzle migration history in `supabase/migrations/`** can be truncated and rewritten. Since PoC has no real data, wiping the running Supabase project's tables and re-running a different migration path is cheap.
- **Application-layer code** written against Drizzle will need rewriting if we switch — the switching cost is real but bounded to the CRUD layer, which is confined to `src/db/` and `src/app/api/patients/`.
