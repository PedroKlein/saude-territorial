# Drizzle Data Access

## Status: placeholder

This skill exists to establish the **library boundary** during the cleanup pivot. Concrete schema, query, and migration patterns will be filled in during pivot execution when the `patients` + extension-table model is designed. Until then, treat the "Boundary rules" section below as authoritative.

## Locked decisions (from planning)

- **Drizzle is the data access layer.** Not Prisma, not raw Supabase-JS. See `docs/adr/ADR-002-drizzle-orm.md`.
- **Schema in TypeScript** — `src/db/schema/*.ts`, exported types via `typeof table.$inferSelect`.
- **Migrations as SQL** — generated by `drizzle-kit generate`, committed to `supabase/migrations/`, applied via `drizzle-kit push` (dev) or `drizzle-kit migrate` (staging/prod later).
- **Base + extension table pattern** — a single `patients` table for shared fields (CNS, name, address, lat/lng), one extension table per condition (`gestantes_data`, `tuberculose_data`, `has_data`), joined via patient FK. Extension tables have `patient_id` as PK + FK with `onDelete: 'cascade'`.
- **No RLS in MVP** — see `docs/adr/ADR-002-drizzle-orm.md` "Consequences → negative". Explicit user-check gates in every route handler compensate.

## Boundary rules (enforced now)

1. **Any query or mutation against a Postgres table goes through Drizzle.** No exceptions.
2. **Supabase-JS is banned for `.from(...)` calls.** If you find `supabase.from("patients").select(...)` anywhere, delete it and rewrite in Drizzle.
3. **The DB connection lives in one place:** `src/db/client.ts` will export a single `db` client that all code imports. No ad-hoc `postgres()` calls elsewhere.
4. **Service-role DB access is banned in route handlers.** Admin scripts (seed, backups) may use a service-role connection, but user-facing API routes must not.
5. **Migrations are SQL files** committed to `supabase/migrations/` — Drizzle-generated, not hand-written unless there's no other way (e.g., adding a Postgres extension). Never edit an already-committed migration; add a follow-up.
6. **The pre-DB-mutation gate** — any script that runs `drizzle-kit push`, `drizzle-kit migrate`, or otherwise mutates a running Supabase project MUST verify the target is non-production before proceeding. Pattern: read `SUPABASE_URL`, refuse unless it matches a whitelisted dev/staging pattern OR both `SEED_SYNTHETIC=1` and `I_HAVE_VERIFIED_NON_PROD=1` are set.

// src/db/client.ts  — indicative
import { drizzle } from "drizzle-orm/postgres-js";

import * as schema from "./schema";

const client = postgres(connectionString, { prepare: false });
export const db = drizzle(client, { schema });

## Query patterns (post-pivot targets, not yet implemented)

```typescript
// Read patient with condition data
const patient = await db.query.patients.findFirst({
  where: eq(patients.cns, cns),
  with: { gestantes: true },
});

// Upsert patient by CNS
await db
  .insert(patients)
  .values(newPatient)
  .onConflictDoUpdate({
    target: patients.cns,
    set: { ...newPatient, updatedAt: new Date() },
  });

// Insert condition data (extension row)
await db.insert(gestantesData).values({ patientId, ...gestanteFields });

// Delete cascades to extension rows via FK ON DELETE CASCADE
await db.delete(patients).where(eq(patients.id, id));
```

## Anti-patterns

- Writing raw SQL strings in route handlers — use Drizzle's typed builder.
- Duplicating column names across schemas — extension tables `include` from `patients` via FK, they don't copy `nome`/`cns`.
- Silent CNS collisions — surface with a "add condition to existing patient" flow, don't auto-merge.
- Skipping the pre-DB-mutation gate on seed/migration scripts.
- Committing seed data with real patient information — LGPD violation. Synthetic only, sourced from `extensao-gat4` sister repo.
