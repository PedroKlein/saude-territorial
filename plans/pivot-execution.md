# Plan: Pivot Execution

> **This is the follow-on to `plans/pivot-cleanup.md`.** Cleanup produced a repo where Sheets is gone and 34 synthetic patients render from a temporary in-code mock at `/api/patients`. This plan wires the app to **Supabase-as-source-of-truth via Drizzle**, ships full CRUD, and migrates the synthetic seed into the database.

## Destination

A repo where:

1. **Drizzle ORM is installed and configured** with a single `src/db/client.ts`, a `drizzle.config.ts` at repo root, and a `pnpm db:*` script surface (`db:generate`, `db:push`, `db:studio`, `db:seed`).
2. **Schema lives in `src/db/schema/*.ts`** as Drizzle TypeScript definitions — a base `patients` table + one extension table per priority condition (`gestantes_data`, `tuberculose_data`, `has_data`) + a `geocode_cache` table for Nominatim results.
3. **Initial migration `0001_init.sql`** is generated by `drizzle-kit`, committed to `supabase/migrations/`, and applied against a dev Supabase project (never production).
4. **Synthetic seed** from `extensao-gat4` is loaded into the dev Supabase project via `scripts/seed-patients.ts`, gated behind `SEED_SYNTHETIC=1` + `I_HAVE_VERIFIED_NON_PROD=1`.
5. **`/api/patients` returns real Supabase rows** joined with their condition-specific extension row, in the shape `{ layers: { gestantes: [...], tuberculose: [...], hipertensao: [...] } }` that `usePatientData` already consumes. The temporary mock (`src/lib/demo-data.ts` + inline `/api/patients` handler) is deleted.
6. **Full CRUD ships end-to-end:**
   - `POST /api/patients` — create with CNS-collision surfacing (`409` + existing-patient payload → UI offers "adicionar condição").
   - `PATCH /api/patients/[id]` — edit fields, re-geocode on address change, persist manual pin drags.
   - `DELETE /api/patients/[id]` — cascade-delete extension rows via FK.
7. **UI reaches feature parity for the 3 priority layers:**
   - "Adicionar paciente" button in the header + right-click-map affordance that opens a modal form with a condition selector and condition-specific subforms.
   - "Editar" reactivated in `PatientDetailPanel`, with address changes triggering re-geocoding.
   - Draggable markers persist `lat/lng` and flip `geocode_status` to `'manual'`.
   - "Excluir" button behind a confirm dialog.
   - CNS-collision dialog on create.
8. **Alert rule config trimmed to the locked 4 rules** for Gestantes/TB/HAS (see LOCKED table below).
9. **ESLint 9 flat config migration** — `.eslintrc.json` replaced by `eslint.config.js` (or `.mjs`) so `pnpm lint` runs green.
10. **All quality gates pass:** `pnpm type-check`, `pnpm test`, `pnpm lint`, `pnpm build`, `pnpm dev` boots and map renders real-Supabase data.

## Mandatory pre-DB-mutation gate

Any task in this plan that runs `drizzle-kit push`, `drizzle-kit migrate`, or otherwise mutates a running Supabase project **MUST** call `scripts/verify-non-prod-db.ts` first (introduced in **PE-1**). Task ACs referencing DB mutation explicitly cite this gate.

Implementation contract:

```ts
// scripts/verify-non-prod-db.ts — runs before any destructive DB step
// Known non-prod project refs. Extend when adding a new dev/staging project;
// removing a ref should be a deliberate PR-level decision.
const KNOWN_NON_PROD_REFS = [
  "gplnvzxtqpqyznqiysza", // saude-territorial PoC (the only Supabase project as of PE-0)
] as const;

const url = process.env.DATABASE_URL ?? "";
const matchesPattern = /localhost|127\.0\.0\.1|-dev\.|staging|test/.test(url);
const matchesWhitelist = KNOWN_NON_PROD_REFS.some((r) => url.includes(r));
const explicitOptOut =
  process.env.SEED_SYNTHETIC === "1" &&
  process.env.I_HAVE_VERIFIED_NON_PROD === "1";

if (!matchesPattern && !matchesWhitelist && !explicitOptOut) {
  console.error(
    "Refusing to run: DATABASE_URL host does not match a dev/staging pattern, is not in the known non-prod whitelist, and no explicit opt-out is set.",
  );
  process.exit(1);
}
```

The gate blocks the destructive step, not the whole plan. If the reviewer decides to relax to `SUPABASE_URL` matching, that decision is in-scope for PE-1 and does not require re-planning.

- **T2.3a** Consulta acompanhamento — model the 1º–9º mês tracking (cols Z–AH on the TB tab).

  **Decision to make in this task, not in advance:**

  - **Option A — JSONB on `tuberculose_data`.** Add `consultasAcompanhamento JSONB DEFAULT '[]'::jsonb` — array of `{mes: 1..9, realizada: bool, data: date?}`. Fewer joins, harder to query, easier to migrate.

  **Recommendation:** Option B. TB treatment analysis is a real reporting use case post-MVP; JSONB would need un-nesting SQL later. Cost is one extra schema file and one extra migration table.

  - **AC:** Whichever path is chosen, a comment in `src/db/schema/tuberculose.ts` cites the tradeoff and links to this task.
  - **AC:** If B: `tuberculose_consultas` has a `CHECK (mes BETWEEN 1 AND 9)` constraint.

## Risks & mitigations

- **Nominatim quota during batch geocoding.** The seed script (T3.1) inserts pre-geocoded lat/lng from source files, so it does NOT call Nominatim. Edit-flow geocoding is one-at-a-time and stays under 1 req/s. If the reviewer later asks for a bulk-import path, that task must revisit the rate-limit story.
- **Deterministic synthesised CNS collisions.** CSV rows in `pacientes.csv` share the same `id` domain as JSON gestantes if they overlap. Mitigation: synthesise CSV CNS with a distinct prefix (`8xxx…` — the seed adds a leading `8` before hashing) to guarantee non-collision with JSON CNS (which start with `1`, `2`, `3`, `4`, `5` per the demo data patterns).
- **`ig` staleness.** `gestantes_data.ig` is a snapshot; if no edits happen for months, the stored `ig` drifts from reality. Mitigation: the API layer recomputes `ig` from `dum` on every read (T4.1) — but only for the API response, NOT written back. The stored value stays as-is until a genuine edit. Alternative (post-MVP): a Postgres generated column or a background job. Not needed for MVP.
- **Optimistic-update rollback on drag-end fail.** If a drag persists but the server rejects, the marker snaps back — Leaflet's marker doesn't automatically reflect a Zustand rollback. Mitigation: `useUpdatePatient` sets a local `pendingPosition` in `mapStore` that the marker reads; on rollback, `pendingPosition` clears and the marker reads the DB position. Implement in T5.5.
- **Zod schema drift between client and server.** The create/edit forms share Zod schemas. Mitigation: export the schemas from `src/lib/patients/schemas.ts` (a lib module, not an API file) and import from both sides. No API-scoped schemas.
- **CNS collision UX.** Users may enter a CNS that appears elsewhere and be told "adicionar condição" — but the existing patient may belong to a very different context (name mismatch, wrong address). Mitigation: the 409 payload includes `nomeCompleto`; the dialog shows it so the user can bail out.
- **`hipertensao` layer vs `has_data` table naming.** Layer id `hipertensao` in code, extension table `has_data` in SQL. Deliberate — SQL uses the standard clinical abbreviation, code uses the SPEC's layer taxonomy. Documented via inline comments in `src/db/schema/has.ts` and `src/config/layers.config.ts`.
